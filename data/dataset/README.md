# Synthetic dataset: customer-outreach pipeline

All data is synthetic. Snapshot date for every record: **2026-10-27**. Generated by `generate_dataset.py` (seed `20261027`, deterministic). `validate_dataset.py` re-derives every expected result independently and reports PASS/FAIL.

## Files

| File | Rows | Grain | Notes |
|---|---|---|---|
| `customers.csv` | 222 | one per customer | Includes 6 **protected test fields** (date_of_birth, gender, home_address, phone, national_id_last4, credit_score). Step 1 must drop them. |
| `billing.csv` | 2,102 | one per bill | Up to 12 monthly bills per postpaid customer. Prepaid customers have none. |
| `consent.csv` | 222 | one per customer | |
| `contact_history.csv` | 526 | one per message | Replaces the old `prior_messages` list. |
| `offer_catalog.csv` | 8 | one per offer | Read-only input. Contains deliberate traps (see below). |
| `ground_truth.csv` | 222 | one per customer | **For evaluation only. Never feed it to the pipeline.** |

Derived fields (`overdue_days`, `last_contacted_days_ago`) are **not stored**. The context builder computes them from `snapshot_date`. Expected values are in `ground_truth.csv`.

CSV conventions: UTF-8, ISO dates (`YYYY-MM-DD`), booleans `true`/`false`, NULL = empty cell, money as `DECIMAL(10,2)` strings (read with `dtype=str` and convert to `Decimal`, never float). Keep `national_id_last4` as a string, because about 10% have leading zeros.

## Reference rules used to build the answer key

Put these numbers in the policy config. If you change a threshold, regenerate.

**Segments (step 2).** Every rule that matches is listed in `expected_all_segments`. The primary segment is the first match in this order:

1. `payment_reminder`: an unpaid bill (`due`/`overdue`) that is overdue or due within **7 days**. The target bill is the oldest such bill.
2. `dormant`: `last_activity_days >= 30`.
3. `declining_activity`: `activity_prev_30d >= 10` and `activity_30d <= 70%` of `activity_prev_30d`.
4. `loyalty_candidate`: `tenure_months >= 24` and tier Gold/Platinum, and either prepaid, or `bills_issued_last_12 >= 6` with on-time payments >= 90%.
5. `consistent`: none of the above.

**Strategy (step 4).**

| Situation | message_type | strategy |
|---|---|---|
| Due today to 7 days ahead | payment_reminder | courteous_reminder |
| Overdue 1–15 days | overdue_notice | overdue_stage_1_polite |
| Overdue 16–30 days | overdue_notice | overdue_stage_2_firm |
| Overdue 31+ days | overdue_notice | overdue_stage_3_final (`human_review_required = true`) |
| consistent / loyalty / declining / dormant | appreciation / reward_offer / reengagement_offer / reengagement_offer | warm / celebratory / helpful / win-back |

**Pre-check gate (step 3).** All checks run. `expected_block_reason` is the first hit in this order:

1. `account_inactive`: status suspended or closed.
2. `data_conflict`: facts contradict each other (codes in `expected_data_conflicts`): paid but amount short, overdue but fully paid (paid yesterday, not yet posted), status vs. due-date mismatch, missing currency, `dormant` but activity in the last 30 days, tier vs. points mismatch, on-time count vs. billing rows mismatch, consent date in the future.
3. `email_not_allowed`.
4. `consent_missing`: **payment reminders need `service_consent`; everything else needs `marketing_consent`.**
5. `email_undeliverable`: no address, or `email_status` bounced/unverified.
6. `dispute_or_complaint_open`: any bill with `dispute_open`, or `open_complaint`.
7. `payment_arrangement_or_hardship`: payment reminders only, flag on any unpaid bill.
8. `cooldown_or_duplicate`: any message sent less than **7 days** ago, or the same `message_type` sent less than **14 days** ago.

**Offer validator (step 5).** Offers of the matching message_type are tried in `priority` order. The first one that passes all of these is chosen:

- **Group:** segment is in `eligible_segments`, and `plan_type` is "any" or matches.
- **Expiry:** `valid_from <= snapshot <= expiry_date`.
- **Channel:** `channel` is email or any.
- **Tenure:** `tenure_months >= min_tenure_months`.
- **Repeat guard:** the same `offer_id` was not sent in the last 90 days.

If no offer passes, the message is sent without one. Blocked customers get no offer.

Catalog traps: `OFR-RWD-SMS` is SMS-only and must never be picked for email. `OFR-REE-EXP` expired on 2026-10-20. `OFR-REE-FUT` only starts on 2026-11-15. `OFR-RWD-500` needs 36 months' tenure and postpaid.

## Coverage

| Scenario group | Customers | What it tests |
|---|---|---|
| clean_* | 100 | 20 per segment, all should draft |
| block_* | 56 | each stop sign, 7–8 cases across segments |
| conflict_* | 9 | each data-conflict type |
| edge_* | 41 | thresholds: activity 29/30 days, decline 70%/72%, low baseline, due in 7/8 days, overdue 1/15/16/30/31/45, cooldown 6/7, duplicate 13/14, tenure 23/24, points 1999/2000, on-time 11/12 vs 10/12, prepaid loyalty, partial payments, marketing-off-but-reminder-OK, service-off-but-offer-OK, missing first name, non-English language |
| offer_* | 10 | every offer test, including expired, future, SMS-only, tenure, plan and repeat |
| multi_* | 6 | several stop signs at once; checks ordering |

Outcome: 149 draft / 73 blocked. Primary segments: payment_reminder 68, consistent 45, loyalty_candidate 43, dormant 34, declining_activity 32. Postpaid 183 / prepaid 39. Languages: en, hi, ta, te, kn, mr, bn.

The mix is balanced for test coverage, not for realism. A real base would be mostly `consistent`. To test with a realistic mix, sample from `clean_*` more heavily.

## Using `ground_truth.csv`

Join on `customer_id` and compare per step:

- step 2: `expected_segment`, `expected_all_segments`, `expected_reason_code`
- step 3: `expected_outcome`, `expected_block_reason`, `expected_all_block_reasons`
- step 4: `expected_message_type`, `expected_strategy`
- step 5: `expected_offer_id`
- step 7 numbers check: `expected_target_bill_id`, `expected_overdue_days`, `expected_amount_outstanding` (target bill), `expected_total_outstanding` (all unpaid bills overdue or due within 7 days), `expected_greeting_name` (falls back to "Customer")

`scenario_tag` says what each customer is testing, so you can slice failures by tag.
